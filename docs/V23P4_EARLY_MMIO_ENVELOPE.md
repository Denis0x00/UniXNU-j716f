# V23P4 r1：遗留 BCM MMIO 前后包络诊断

V23P4 r1 保留 V23P2 的标题、方块和原始 `DSB SY`，修改入口遗留写入点
`0xfffffff0073fe32c` 并为后续清屏增加两个矩形的保留过滤器。原来的 `str w1, [x0]` 被一个 branch 包住：

1. 清黑两个标记及中间间隙，排除上次启动留下的像素；在 `(1280,192)` 绘制 96×96 前方块；
2. 原样执行 `str w1, [x0]`（当前值为 `0xf0`）；
3. 在 `(1384,192)` 绘制 96×96 后方块；
4. 返回 `0xfffffff0073fe330`，继续原始 `isb`。

两个方块都在此前已验证的 framebuffer 保留区内。stub 使用现有代码洞，未新增
内存映射、表项、固件模块或 MMU 设置。

刷前复核发现原版 P4 的方块会被随后的 P2 清屏擦除；旧版模拟仅执行 stub，
遗漏了后续清屏。旧镜像未刷写，已私有备份并由 r1 取代。r1 在 P2 clear 的
`0xfffffff0073fc574` 处增加过滤器，仅保留两个 96×96 矩形。

## r1 录像结果（2026-10-25）

- 视频共 678 帧，约 22.62 秒；原始视频和逐帧图片保存在私有工作区。
- 1.368 秒首次见绿色入口带，1.435 秒见标题 mode 5、顶部检查点 1/2，以及下方两个 MMIO 标记。
- 四个方块持续可见；检查点 3、EL/SCTLR、A0/SMC/RETURN 均未取得可见记录。
- 17.278 秒仍有诊断画面，17.312 秒消失：从入口带算约 15.94 秒，属于相机时间，不能当作固件计时器结果。
- 后续见 Lenovo / Powered by Android 标志，约 21.08 秒已回到 r1 菜单。它不证明进入了 Android 系统。
- PMIC 从 `0x02000001` 变为 `0x02000041`，复位源和位含义仍未确定。

下方后标记是在原始 `STR` 后绘制，并成功保留至标题阶段。因此已有证据表明
执行越过该指令；但普通 store 可以在外部事务完成前继续执行，这并不证明
MMIO 事务已经完成，也不能据此排除其与后续 `DSB SY` 的关系。检查点 3 未见
只限定了可见进度，不能直接宣判 DSB 卡死。

建议下一步保留相同包络、清屏过滤和检查点，对比原始 `STR` 与 `NOP`。
此前 P3A 缺少这套相同的可见记录，不能替代此对照。

用户要求下次编译缩小菜单文字：V23 菜单源码 `Config.Scale` 已从 4 改为 3，
线性字号缩小 25%，尚未编译或刷写；内核诊断字体未改。原 r1 菜单库源码已
私有快照，逐文件匹配 `remote-build.json`。下次构建应显式审计菜单模块差异，
不能继续声称全部非 payload 模块与 P2 一致。

## 真机解释

- 只见前方块：前格写入已可见，未取得后格的可见记录；候选包括 MMIO 未返回、后格绘制前后异常或显示写入可见性问题，不能单凭此判定 store 卡死。
- 前后方块都见到、标题仍只有 1/2：原始 MMIO 写入已经返回，故障点应在其后，不应继续把该写入当作已证实根因。
- 两个方块都没有：未到达包络，或显示记录本身未完成；需要结合标题和已有方块判断。

任何随后出现的 Lenovo/Android 启动画面都只表示设备后来重启，不能单独证明 PSCI 或 watchdog。

模拟中的 MMIO 是 RAM。原始 store 返回后到 pre 之间的 ISB/TLBI/IC/MSR/TTBR/vector
路径没有模拟执行；清屏测试显式从 pre 进入。检查了该原始路径不读取包络使用的
x9..x14，且包络保持 x0/x1、x15..x30 和 SP。真实总线顺序、权限和复位仍需真机录像。

当前镜像仍是单核、MMU 前终止诊断；counter、持续 MMU、ArmCpu、UFS、root 和用户态不在本版范围。
